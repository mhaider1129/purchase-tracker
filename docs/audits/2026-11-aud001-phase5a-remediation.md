## Current root causes and reproduced evidence

AUD-005 already established explicit permissions, institute/reference checks, contract root locking, a shared transaction and transactional audits. The October finding's absence-of-transaction/concurrent-create explanation is therefore partly superseded. Those fixes are retained rather than duplicated.

The remaining defect is competing financial authority: legacy `contract_invoices`, `contract_payments`, `contract_consumption` and manually writable contract counters have no mandatory canonical invoice-match/verified-voucher/posted-payable/allocation prerequisite. Payment creation can default to `paid`, allow an absent invoice, and accept currency inconsistent with the invoice. It checks accumulated paid value only on creation; payment edits and status changes do not repeat that check. Header paid projections count every payment except rejected/cancelled, including pending/approved rows, whereas invoice paid status counts only `paid`. Editing a payment does not synchronize the contract header. There is no legacy payload-bound idempotency key.

The real PostgreSQL probe ran the unchanged master handlers in a detached worktree, using a newly created empty loopback-only PostgreSQL 16 container reconstructed from the repository's supplied exports and manual schema. No production data or provider was used. Fixture observations:

| Probe | Unchanged master result |
| --- | --- |
| Repeat the identical logical payment, amount 30 against invoice net 100 | Both return 201; two rows, total paid 60 |
| Concurrently edit those two payments to 60 each | Both return 200; actual paid 120, invoice status `paid`, contract header still 60 |
| Edit payment currency from USD to EUR for a USD invoice | 200 |
| Create payment without an invoice | 201 |
| Hard-delete a request referenced by a contract with unmatched historical paid amount | 200; contract remains but its `source_request_id` is cleared |

The concurrent edits serialize under AUD-005's root lock but still overpay: locking does not replace the missing business invariant. The generic `deleteRequestCompletely` discovers foreign-key children and deletes or nulls their links. It was another active financial-history/provenance writer. The new retention check rejects financial-history deletion/detachment before this traversal.

The reproducible probe is `node scripts/testBackendContractRefresh.js --contract-settlement --legacy-settlement-probe` on the baseline worktree with the new disposable runner/test file copied in. It does not bypass a policy: it invokes whichever actual handlers the checkout contains. Running it on the remediated checkout cannot re-enable legacy settlement. The probe writes only fixture observations to `/tmp/aud001-baseline-observation.json`; no live dataset is committed.

## Authority and amount semantics

| Amount / action | Existing owner | Interpretation and overlap |
| --- | --- | --- |
| Commercial contract commitment | Contract terms/items/governance | Agreement ceiling, commercial commitment and contractual capacity; not a budget ledger entry, receipt or payable. |
| PO commitment | `purchaseOrderService` + active encumbrance in `commitment_ledger` | Created at governed PO issue, reduced/actualized or released by existing canonical commands. PR estimates/manual commercial values are not interchangeable with it. |
| Received value | Canonical receipt/technical acceptance quantities × source PO prices | Held/rejected units are not accepted payable capacity. Receipt value is not invoiced or paid value. |
| Invoice creation | `supplierInvoiceService.submitSupplierInvoice` | Canonical supplier identity, PO/line provenance, invoice number/date/currency, payload-bound retry. Legacy contract invoice representation previously overlapped; it is now immutable history. |

| Liability recognition / AP posting | Verified voucher → `apPostingService.postApVoucher` | `finance_postings`, posted `ap_payables` and commitment actualization. Draft/submitted invoices, contract counters and voucher creation alone are not posted liability. |
| Payment allocation / completion | `paymentService.postPayment` | Exact decimal, locked posted payable, canonical allocations and idempotency. `PAID` is ERP-recorded settlement, not independent bank reconciliation. Legacy payment status/header changes previously overlapped and are now blocked. |
| Contract balance / consumption | Existing contract summary/consumption readers | Legacy headers and invoice/payment/consumption sums remain historical projections. Full payment preparation/approval/reversal policy and operational internal-GL completeness are **not** established by this containment patch. ## Duplicate-settlement analysis

Canonical invoice identity currently uses supplier ID plus lower/trimmed invoice number (with database uniqueness), and separate payload-bound command idempotency. Invoice date, currency, amount, PO/line identity and attachment/source content contribute to validation/fingerprints; these are not all interchangeable natural keys. Canonical payments use a command idempotency key/fingerprint plus explicit payable allocations, posted authority, currency and remaining-balance locks. Several installments against one invoice remain legitimate.

Legacy invoices check duplicate number/supplier inside a contract using application matching flags, rather than sharing the canonical namespace/constraint. Legacy payments have no shared payable/allocation or payload-bound retry identity. Request IDs, contract references, equal record IDs across tables, supplier names, dates, amounts and payment references alone cannot prove that two ledger entries represent the same obligation or settlement. No new duplicate constraint/key is introduced; legitimate installments and credit/FX histories are not deleted, merged or rejected by an invented identity rule.

**Residual risk:** a canonical operator can still recreate/pay an old legacy obligation if its historic source is not reconciled first. Phase 5A freezes the competing new legacy path; it does not manufacture a cross-ledger mapping or silently prevent legitimate canonical payments using heuristics. Operators must not replay a previously settled obligation. Verified contract-only/no-PO source adaptation, credits, authorized FX, retainage, refunds and reconciliation-approved opening balances remain a later design/cutover package.

## Read-only reconciliation report

`purchase-backend/sql/reports/aud001_phase5a_reconciliation.sql` and `scripts/lib/contractSettlementReconciliation.js:collect` implement the report specification. There is no hosted CLI connection, app route, scheduled job or automatic repair. The caller must supply a **dedicated idle diagnostic client**, an explicit positive institute ID, and explicitly opt into unowned rows if needed for owner review. The helper starts one `REPEATABLE READ READ ONLY` transaction, verifies read-only mode and rolls it back. It imports no application connection, bootstrap or environment credentials. No live report was run by this task.

Rows cover legacy invoices/payments/consumption, canonical supplier invoices, posted payables, canonical payment records/allocations and contract counter/capacity evidence. Evidence includes exact decimal strings, supplier/invoice/date/currency, contract/PO/voucher/payable/allocation references, recorded status, separately labelled gross/net/retention/penalty values and per-currency legacy paid totals. Missing ownership and ambiguous supplier names are explicit; names never establish identity. Unsupported credits/advances/reversals remain evidence for review.

| Classification | Meaning |
| --- | --- |
| Confirmed match | Consistent **internal canonical** FK/posting/allocation provenance. This never means a confirmed cross-ledger duplicate, bank settlement or final financial-control certification. |
| Possible match | Same-institute canonical supplier/bill identity or corroborating payment reference/value/currency candidates. No immutable legacy-to-canonical mapping is available. Installments remain separate rows. |
| Unmatched | Sufficient basic identity but no candidate; a counter/capacity record without a proven canonical mapping is also not silently matched. |
| Conflicting | Known provenance, represented currency/date/gross amount, legacy duplicate bill identity or linked-record inconsistencies need review. No repair follows. |
| Insufficient evidence | Missing institute, supplier, bill/date/currency/source, unsupported credit/reversal/consumption basis or incomplete canonical linkage. Unknown values are not converted into confirmed zeroes or identities. |

Candidate IDs are typed by row kind: legacy invoice → canonical supplier invoices; legacy payment → canonical payment records (candidate invoices are separately in evidence); posted payable → supplier invoice; canonical payment record → payables. Numeric IDs from different namespaces never establish a match. Amount/date/ref equality is a review hint only. Contract-to-PO/receipt aggregation is not invented from a free-text reference or common request; remaining contractual capacity requires an approved attribution model.

Keep any owner-run output private; do not commit real invoices, supplier/bank details or raw transaction captures. Large history volumes need bounded operational performance review. Hosted RLS, grants, custom functions/triggers, actual historical data and bank/GL reconciliation remain unverified.

## Containment and operational compatibility

- Eight legacy financial mutation handlers now return **410 `LEGACY_CONTRACT_FINANCIAL_MIGRATION_REQUIRED`** after existing fresh authorization, institute and child-reference validation. This includes invoice metadata/matching/status, payment creation/edit/status and manual consumption. Unauthorized/foreign callers retain 401/403/404 failures; a 410 is not an authority grant.
- Changed or imported paid/consumed header amounts are blocked through create/edit/renew. Exact unchanged amounts remain usable without rounding/truncation; null resets cannot erase stored history. New empty roots remain supported. Ordinary legal/commercial contract edits, lifecycle, terms, documents, obligations and renewals remain in their existing workflows.
- Historic GETs, financial summaries and stored records remain available through existing AUD-005 scope/finance checks. No historical invoice is marked paid, amount backfilled, source identity guessed or balance corrected. Existing summaries retain their legacy formulas/limitations.
- Financial request hard-delete returns 409 before FK traversal; it cannot erase canonical financial rows or detach unmatched contract settlement sources. Ordinary nonfinancial request deletion remains supported. Records with retained financial evidence should be preserved for reconciliation; this is not a financial cancellation/reversal implementation.
- Supported new settlement uses existing canonical invoice submission/matching/verification, voucher verification/posting and an open payable payment command with its existing required permissions, receipt/technical evidence and idempotency. No-PO/unmapped contract settlements and historical edits/imported balances are **unsupported pending reconciliation/source-adapter work**. No route transparently redirects or generates liabilities.
- Commercial contract ceiling/commitment configuration and requested-item compatibility snapshots remain separate from canonical liability/settlement authority. This patch does not redesign those unrelated workflows or certify their projections as accounting balances.
