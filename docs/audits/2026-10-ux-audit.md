# October 2026 — frontend navigation and usability audit

Reviewed baseline `f254a6da68ae8268a8afc0149dd903ed10f42de5` on 30 October 2026 (Asia/Baghdad). Documentation-only audit. See [system audit](2026-10-system-audit.md) for finding definitions, complete evidence and test limitations.

## What is implemented now

The application has a shared Axios client (purchase-frontend/src/api/axios.js), centralized explicit session-expiry handling, App.js routes and permission/resource-aware navigation. Request workspaces and request-specific P2P routes coexist with global P2P lists. Technical landing is a task worklist with filtered cards, department/review/status/date filters, scoped historical detail and Management responsibility setup. Maintenance request scorecards now derive from matchingRequests; they are not still hard-coded global totals. Whole-request departmental ranking/placement and institutional priorities are implemented. Surgical departments/automatic team routing and supplier-backed demos are present.

These are source-confirmed features. No live browser, clinical-user observation, mobile, screen reader, Arabic typography or completed-production-workflow study was performed. UI concerns below are source-based observations and proposed validation, not measured user failure rates.

## Prioritized UX recommendations

1. Fix authorization and financial/lifecycle authority before hiding or consolidating controls. UI visibility is not a security repair.
2. Publish a shared status vocabulary: operational completion, physical/technical acceptance, requester receipt and financial settlement. In-stock fulfillment should not look like waiting procurement; current shared fulfillment SQL is a positive control to reuse.
3. Reduce technical form manual entry from authoritative request/PO/product/supplier data, preserving conditional basis/evidence and changed-proposal rounds. Keep clinical judgment fields explicit.
4. Add role-oriented task panels and meaningful action-disabled explanations (missing routing, pending acceptance, stale version, changed proposal). Provide progress and resume paths.
5. Validate Arabic RTL, dates (Baghdad inclusive boundaries), Excel column semantics, keyboard interactions and screen-reader labels with a representative clinical/SCM/receiver/finance walkthrough. Existing component tests are not proof of those behaviors.
6. Re-establish clean lint/strict build before broad component extraction. AUD-017 details exact existing failures. Do not turn off CI warnings to make the build appear healthy.

AUD-016 records the confirmed component complexity observation with its evidence and limits; AUD-011/AUD-018 address status/reporting integration. These recommendations are not implemented in the audit PR.
