Only synthetic hospital/institute/user/item/supplier/financial fixtures are allowed. Do not copy production Supabase data, dumps, credentials, patient identifiers, settlement records or bank details. `node scripts/databaseRelease.js verify --connection-mode runtime --environment staging --release <exact-tested-SHA>`

The existing CLI opens a read-only transaction. Host-generated `DB_RELEASE_READONLY_URL` selects the same local `purchase_backend` identity as the application. No role override, owner login, hosted URL, schema profile override, receipt insertion or approval-engine activation is permitted. Backend startServer then repeats its normal fail-closed startup verification before workers/listening. DB failure occurs before planned maintenance or stopping the previous service.

## Application rollback and crash recovery

Before handoff, DB verification and container preparation occur while the previous application remains active. Handoff displays maintenance, stops/verifies the previous worker process, starts and checks the candidate, validates/reloads the gateway route and verifies its release marker. Stopped previous containers, images, runtime files and upload directories are retained. No global Docker prune, source force update or destructive data cleanup exists.

An approved rollback selects only the exact retained previous commit. Its DB compatibility is verified **before** stopping the current application. If intervening schema changes invalidate that version, rollback is blocked; use an approved forward repair or separate database recovery plan. Application rollback never runs SQL rollback, resets stock, reverses accounting or restores a snapshot over new records.

Agent crash during `PREPARED`, `HANDOFF` or `RECOVERY_REQUIRED` refuses blind replay. Review the fsynced state/audit journal and independently approve `recover` for the retained previous SHA. Recovery stops known candidate/previous processes, verifies DB compatibility, starts the retained previous release, proves health and restores its route. If recovery fails, keep maintenance, report failure and escalate. The first deployment has no previous release; failed initial activation stays explicitly unavailable.

OS `flock` releases automatically when its process/container dies. State transitions persist; do not delete lock/state files, edit state to ACTIVE, restore a different volume or fabricate success to bypass recovery. After the terminal operation outcome is durable, a crash before GitHub acknowledgment can be acknowledged without repeating business mutations. ACTIVE alone does not prove command completion: an interrupted terminal write requires separately approved recovery. Failed status delivery retries only the recorded acknowledgment.

Test disk-full/audit-write failure, proxy/GitHub outage, database loss, gateway validation/reload failure, process termination at each transition, host reboot/missing volume and failed prior-release startup externally before acceptance. Local adapter tests prove sequencing/failure decisions, not real host networking, crash durability or external traffic recovery.

## PR109 correction: durable command outcomes

The authoritative `state.json` now uses version 2: deployment state, an append-only logical operation history, and the currently fenced operation share one fsynced atomic replacement. Existing disabled-infrastructure deployment state is read without discarding its release. A handled-file cache without a bound command ledger requires review; it is never permission to execute an old request again.

Before any application effect, the controller records the exact GitHub run/attempt, operation, target SHA, workflow SHA, authenticated artifact ID/digest, identity hash and deployment-record ID. It persists before/after effect boundaries and deployment phases. A terminal `SUCCEEDED` or safely recovered `FAILED` outcome is committed before writing the handled cache or sending status. Lost caches and failed acknowledgments are reconstructed from this ledger, including successful rollback/recovery; they do not run the command again.

An interrupted effect or state-write failure remains uncertain. The same identity is fenced, and a new ordinary deploy/rollback cannot overtake it. Only a fresh independently approved `recover` request may supersede it, selecting the recorded release. This is not a distributed exactly-once transaction across Docker, disk and GitHub: unknown effects require review rather than automatic replay. GitHub status delivery remains at-least-once. Retain the ledger with the staging backup; do not delete entries to retry an operation.

Local reconciliation runs before polling and in its finalization path, independently of GitHub token/API/download/acknowledgment availability. A stopped release, uncertain operation, interrupted phase or failed HTTPS route enters verified maintenance without automatically restarting services. `health.json` records phase, operation identity, first-observed time, current check time and the required action; `poll.json` reports GitHub availability separately. The loaded maintenance marker is checked before reloading, preventing repeated maintenance/restart loops. Failure to establish maintenance requires manual gateway intervention. These records and command transitions must be monitored and retained.

A timed-out or killed mutating Docker client does not prove the daemon canceled its effect. Such operations stay fenced and never automatically restart the previous worker generation. Before approving recovery, the operator must settle/inspect the Docker daemon's pending operation and recorded resources; do not assume a timeout is a confirmed rollback.

## PR109 follow-up: preserved recovery context and independent uncertainty fence

An approved recovery persists `deployment.recoveryContext` before preflight. It retains the complete original active/previous release capsules, a hashed original-state snapshot, the selected target, authenticated operation identity, attempt history, stage and unresolved status. Neither `previous` nor retained containers are scratch storage for recovery eligibility. A second independently approved request can still select the original previous release after interruption, including a crash immediately after the recovery handoff checkpoint. The temporary context is removed only in the same durable terminal commit that archives its resolved copy and resolves every inherited uncertain operation.

Uncertainty is independent of the deployment phase: `ACTIVE` does not authorize ordinary deployment while the ledger contains an unresolved operation, failed recovery fence, or recovery context. Starting another recovery only records an attempt; it does not supersede its predecessors. Invalid targets, DB preflight failures, handoff failures, HTTPS failures and failed state writes retain this fence. Successful recovery records the complete bound resolution proof; history and unsuccessful attempts are preserved. A repeated terminal request returns its recorded outcome without replaying effects.

Every mutating Docker boundary has a durable `pendingEffect` before invocation and clears it only after acknowledgment is durably stored. Local health-monitor maintenance reloads use the same pending-effect discipline and are not repeated when their result is unknown. Read-only probes and inspection of stopped containers cannot establish cancellation. Automatic health monitoring still enters maintenance when possible, never automatically starts an application, and preserves corrupted authority files for manual investigation.

### Quiescence prerequisite for uncertain effects

The controller reads the **host kernel boot UUID** from the fixed read-only Compose bind `/proc/sys/kernel/random/boot_id:/run/scop-host-boot-id:ro`. A controller restart, changed container ID, route marker, empty process listing or successful GitHub acknowledgment is not a quiescence proof. The controller does not reboot the host or restart Docker.

- If every inherited mutation has a durably acknowledged completion (`pendingEffect: null` in execution protocol 2), a fresh approved recovery can reconcile the recorded generations on the same boot.
- If a mutation has an unacknowledged outcome, recovery preflight may run but handoff/start/route mutations remain blocked on the same host boot. The operation remains fenced; do not clear/edit it or retry with an ordinary deployment.
- A separately authorized operator must investigate and, when appropriate, arrange a **cold host restart of the dedicated isolated staging host**. Verify storage integrity, preserved state and ownership, Compose `restart: "no"`, and the absence of any unapproved auto-start units before resuming. Never reboot or operate on production or the emergency recovery host as part of this procedure. The newly approved recovery requires a different observed host boot UUID before reconciling recorded resources. An additional uncertain mutation on that boot requires another reviewed boundary.
- Legacy uncertainty lacks an execution epoch. Its first reviewed attempt persists a genuine observation barrier and remains blocked. Only a later observed host boot change can establish quiescence; no historical epoch or execution evidence is invented.
- Corrupt/missing state or a missing/untrusted boot-ID bind requires operator investigation, not automated repair. If authority restoration is necessary, preserve the original bytes and require a reviewed recovery/quiescence plan; do not fabricate successful operations or remove fences.

This conservative host-boundary policy assumes one dedicated host/kernel and one authoritative local Docker daemon, root-controlled read-only bind mounts and durable intact state. It is not sufficient for a remote daemon, cross-host restored state, root compromise, kernel UUID spoofing, VM snapshot rollback, or malicious/out-of-band Docker operations. Those remain activation blockers unless independently resolved. Reboot-based quiescence is covered by synthetic fault models here; actual external host restart/storage durability must be tested during separately authorized activation. The local gateway integration validates actual Docker, PostgreSQL and HTTPS traffic, not an external host reboot.
