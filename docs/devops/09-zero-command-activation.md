# Zero-command release operation and one-time activation

## Owner experience after separately approved activation

1. Describe the enhancement in ChatGPT; ask Codex to implement it and open a PR.
2. Review GitHub checks and the change, then merge the approved PR.
3. Post-merge **master** CI tests the actual merged commit and creates the candidate artifacts. Approved staging automation consumes that candidate; the owner does not synchronize repositories, build again or copy files.
4. Review staging smoke results and the enhancement. Approve UAT through the configured staging-acceptance environment.
5. In **Actions → Deploy to Production → Run workflow**, choose master and enter the successful master CI run ID and its accepted staging run ID from the staging summary. These are evidence selections, not Git/SSH/SQL commands. Do not select a PR or feature-branch run.
6. Read the verified candidate summary, then use **Review deployments → scop-production → Approve and deploy**. Required reviewers and prevention of self-review enforce this approval independently of workflow inputs.
7. Receive GitHub Actions success/failure notifications and read the deployment summary, including exact source/artifact IDs, health status, prior release and rollback readiness. A failed/skipped/blocked run must say **not deployed**, not imply success.

No routine owner `git pull/add/commit/push`, SSH, SQL Editor, migration command or backend/frontend synchronization is part of this operating model. Codex handles source commits/PRs. Approved automation handles delivery, migrations and evidence. Additional production database changes still require their own human approval; zero commands does not mean zero review.

## What is implemented now

- The workflow is explicitly named **Deploy to Production** and exposes only `ci_run_id` and `staging_run_id`. No caller-supplied source branch, SHA, repository URL, download URL, server, script or shell command is accepted.
- Its verification job checks out the immutable workflow/control-plane revision, not code named by a candidate input. It has only Contents/Actions/Deployments **read** permissions and performs GitHub metadata GETs; it does not contact a server/database.
- Selection requires a completed successful master **push** run from this repository's exact code-CI workflow. All mandatory code jobs must have succeeded. A successful fork/PR run is insufficient.
- CI packages `backend-release` from exact committed bytes, rejecting worktree/line-ending drift and excluding environment/local files. `frontend-build` is the already-tested production build. The code manifest records their artifact IDs. The backend source package is not a finished runtime image or proof of target runtime compatibility.
- The verifier requires unique, nonexpired artifacts with GitHub SHA-256 digests and matching producing run/commit. It does not accept an arbitrary typed digest as proof.
- Staging must be a successful same-commit run from the approved staging workflow, with successful `stage-deploy`, `stage-smoke`, `database-compatibility` and `owner-uat-acceptance` jobs. Current disabled placeholder runs cannot qualify.
- A genuine successful staging GitHub Deployment record must bind those exact CI/staging run IDs, source commit and backend/frontend artifact IDs/digests. Its latest status must still be successful and link to that staging run. Fabricated local JSON assertions do not qualify.
- The record must identify the successful same-commit manual isolated database-validation run, with all sixteen configured database jobs successful. Missing/skipped database tests remain blocking.
- Production and staging-UAT environments must expose actual required reviewers, prevent self-review and restrict deployment to protected branches; master must be protected. Missing setup fails verification.
- **The production job is still `if: ${{ false }}` and its placeholder exits with failure if accidentally reached.** It references `scop-production` but contains no deployment executor or credentials. The current result summary explicitly says no deployment occurred and the recovery service remains untouched; the workflow fails rather than presenting a disabled deployment as a successful release. No activation, production verification, staging or SQL execution was performed here.

The verified-selection artifact remains `productionDeploymentAuthorized=false` / `executionEnabled=false`. Metadata selection is not live database compatibility, backup acceptance or permission to deploy. All operational prerequisites below must be completed before enabling an executor.

## One-time activation checklist — separate authorization required

These are administrator/engineering setup tasks, performed through reviewed infrastructure changes and GitHub UI where possible. They are not routine commands for the system owner, and none was executed by this assignment.

1. **Approve source ownership.** Review/merge the source-integrity dependency and automation PR, reconcile independent backend recovery/PG17 branches and the thirteen initial destination conflicts, and preserve all histories/local work. Make combined master the only release authority. Do not deploy from a mutable standalone main branch.
2. **Protect source and approvals.** Configure required PR review and the Code CI gate on master; disallow force pushes/deletion and validate administrative bypass restrictions. Configure `scop-staging`, `scop-staging-acceptance`, `scop-production` and `scop-production-database`, with appropriate required reviewers, no self-approval and protected-master deployment policy. Verify GitHub plan support with a second administrator. The audit found these controls absent; workflow YAML alone cannot configure them.
3. **Approve isolated staging.** Approve its target, access URL, networks, synthetic data, PostgreSQL major/extensions and independent credentials. Implement/test the runtime-image builder, including locked dependencies and target compatibility. Build once in CI, test it and preserve the same runtime digest for staging and production. Source-package provenance alone is not runtime acceptance. Do not provision anything against the recovery service or reuse production data/secrets.
4. **Wire automatic staging.** In a reviewed activation PR, replace the staging fail-stop with an approved isolated executor and an authenticated after-success workflow trigger restricted to master CI. Reject forks/PR artifacts. Run the full disposable database and staging schema/compatibility/smoke gates for the exact candidate. Preserve all sixteen existing DB suites; never execute migrations in PR workflows. Current v1 verifier requires CI/staging/DB workflow run head SHAs to match; older candidates without that provenance remain blocked rather than guessed compatible.
5. **Publish genuine acceptance evidence.** Implement the staging job names above. Use a separately protected `scop-staging-acceptance` job for owner UAT. Only after real deployment, successful smoke/DB checks and UAT may the trusted workflow create/update its GitHub Deployment record. Scope its token's Deployments-write permission to that approved job, not ordinary source CI. Record numeric `source_ci_run_id`, `staging_run_id`, `database_validation_run_id`, exact `commit_sha`, `backend_artifact_id/digest` and `frontend_artifact_id/digest`; use environment `scop-staging`, `production_environment=false`, and a final successful status linking to the actual staging run. Never manufacture receipts just to satisfy the selector.
6. **Resolve production database readiness.** Finish the actual schema/runtime-role/permission/attestation reconciliation under separate authorized access. Verify a recoverable backup and tested recovery plan. Implement bounded preflight evidence for the selected application/schema contract; unit tests and staging alone cannot prove the live production schema. Application-only releases still need compatibility. Any production migration gets a separate environment approval, immutable reviewed forward SQL, preflight/backup checks, transactional/audited execution and preservation postflight. Do not implicitly execute frozen history or recovery bundles. Owner approval occurs in Actions, not a routine terminal/SQL Editor session.
7. **Install the bounded production executor.** Approve its target, identity, network and immutable-artifact interface in a separate PR. It may consume only the verifier's numeric run/artifact IDs and validated digests, never free-form code, a mutable branch, or a new untested server build. Download from the verified run; independently verify downloaded archive SHA-256 before unpacking, and payload/image provenance before execution. Refuse expiry, missing evidence, mismatch or ambiguous outcome; never fall back to HEAD or rebuild an alternative candidate. Use the previously staged runtime artifact. Restrict privileges to candidate release operations and exclude recovery directories/process/port/routing, broad administrator access and arbitrary script execution.
8. **Approve first cutover separately.** Rehearse deployment, health/auth/workflow tests and rollback in staging. Preserve the emergency recovery process and routing until a separately approved traffic-cutover operation. Do not stop, replace or restart it merely by enabling a workflow. Remove the production hard stop only in the reviewed activation change after the real executor, authenticated compatibility/backup checks and environment protections have been verified. A settings toggle alone is insufficient.
9. **Finish status and rollback reporting.** Replace the current disabled-state summary only when an executor exists. On success/failure record source SHA, verified artifact/runtime digests, approvals, operation timestamps, health checks, prior verified release, rollback eligibility and a gated rollback link/procedure. Preserve failed logs safely. Never report a successful deployment without genuine operational evidence. A rollback must select a prior verified release and independently check database compatibility; do not reverse financial/schema data automatically. The recovery service is not an automatic rollback target.
10. **Retire routine manual delivery.** Once validated, disable the old standalone push/deploy hooks and manual-copy process through separately approved changes. Deploy from combined CI artifacts; standalone repositories become downstream reviewed mirrors, not competing release authorities. A future least-privilege synchronization publisher may create destination PRs from clean reviewed plans, preserving destination histories and CI requirements. Do not force-push or enable auto-merge until separately validated. This removes manual backend/frontend synchronization from the owner's release path.
11. **Enable owner notifications.** Configure GitHub Actions notifications/watch settings and access to run summaries/artifacts. Test both a successful staging release and injected failure, and verify that the owner receives failure/rollback information without using SSH or handling secrets in chat.

## Activation acceptance test

Demonstrate the entire sequence with synthetic staging data: request → Codex PR → automatic code checks → approved merge → immutable candidate → staging → smoke/DB/UAT → manual production selection → environment approval → controlled executor result. Also demonstrate wrong run, fork/PR run, artifact expiry/tampering, skipped tests, mismatched staging commit, missing reviewers, latest failed staging status and failed backup/compatibility gates all block promotion. Production remains disabled until the separately approved activation/rehearsal and first-cutover acceptance are complete.
