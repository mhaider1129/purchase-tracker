# External requirements and activation — separate authorization required

**EXTERNAL STAGING IS NOT ACTIVATED.** Both `deploy/persistent/policy.json.externalActivationEnabled` and the persistent request job's literal `if: false` remain hard stops. IaC provisioning requires `activation_authorized=true`; default is false. No apply/plan, provider API, host service or external database operation was run for this assignment.

## Exact external requirements

1. A separately approved Hetzner staging project, staging-only provider token, administrator SSH public keys, region/size quote and restricted admin/hospital VPN CIDRs. No production resource IDs or private networking. `deploy/persistent/terraform/main.tf.json` creates only a labeled staging VPS, firewall and attached ext4 volume, with `prevent_destroy` on server/volume. Provider token must be supplied as the explicit sensitive `staging_hcloud_token`, not copied from production. Never commit Terraform state, tfvars or plan files containing credentials.
2. A dedicated staging hostname such as `staging.<approved-test-zone>`, DNS to the new IP, trusted TLS certificate/key and renewal procedure. The controller rejects the production domain, Supabase hostnames, IP literals and non-staging DNS names. Hospital/VPN HTTPS CIDRs and additional trusted client-certificate CA and individually issued client certificates are mandatory.
3. An independently built/pinned controller image digest from `deploy/persistent/agent.Dockerfile`, a vulnerability/dependency review and host patching procedure. `scripts/persistent/build-agent.cjs` builds from a whitelist without host secrets. The control-plane image must never be substituted by an application capsule.
4. A GitHub App installed only on `mhaider1129/purchase-tracker`, with Actions read, Contents read, Deployments write and Metadata read. Private key, App ID and installation ID remain on staging. No Actions SSH or provider secret is required for routine deployments. No App permissions are created by this PR.
5. Protected master, required code checks, `scop-staging` environment restricted to protected master, required independent reviewers and `prevent_self_review=true`. The agent requires actual approval history and rejects the triggering author as approver. Use a new request rather than rerunning a previous request. Configure `scop-staging-acceptance` reviewers and an agreed hospital UAT record separately; UAT is not inferred from package/deployment success.
6. Encrypted staging-volume backup, tested restoration, alert ownership, retention and capacity limits. Synthetic datasets and staff staging credentials still need protection. A staging backup is not a production restore source.

## One-time approved installation order

These are operator preparation steps after separate provisioning authorization, not commands executed by this change. Review provider syntax/available server types before applying; illustrative size is configurable. Do not import production Terraform state.

1. Apply approved IaC in the separate project. Cloud-init installs base Docker/Compose tooling, writes the staging purpose marker and leaves an activation-pending marker. It does not clone code, install secrets, start staging or run SQL.
2. Mount the attached volume at `/var/lib/scop-staging` using its specific output device, persist the mount and verify it survives reboot. Never format an existing volume. Record the mounted filesystem UUID in `/etc/scop-staging/volume-uuid`; `verify-storage.sh` and mount-ordered infrastructure/controller units must pass before reboot startup. Prepare root-private `gateway/`, `releases/`, PostgreSQL data, and UID 1000-owned `uploads/` and `private/` directories. Bind mount paths must already exist; database `create_host_path:false` prevents silently initializing a replacement directory. Review mount and boot order before enabling anything.
3. Install the reviewed control-plane files under `/opt/scop-staging` and example configuration under `/etc/scop-staging`, with no world-readable key/runtime files. Root config has purpose `wici-isolated-staging-v1`, exact instance and fixed state directory. Create `host-purpose` and verify it matches before firewall installation. Keep `enabled=false`, `databasePrepared=false` and **do not** create `ACTIVATION_APPROVED` yet.
4. Install TLS files under `/etc/scop-staging/tls`, the public client CA trust root under `/etc/scop-staging/access/client-ca.pem`, staging owner secrets in `database-owner.env`, and application `runtime.json` containing only `purpose`, matching `instance`, generated `databasePassword` and `jwtSecret` (32+ URL-safe characters). The agent constructs `database:5432/<scop_staging_...>` itself and accepts no database URL or owner account from a request. Owner DB credentials are not mounted into the agent.
5. Complete the separately approved database initialization/release preparation in document 14. Keep database owner and application role distinct. The agent cannot bootstrap a blank application schema, create receipts, attest a new commit or apply SQL; it will block until those requirements are genuinely satisfied.
6. Approve the profile-based Compose definitions and networking. Start the staging database/gateway/egress infrastructure only under this separate authorization. PostgreSQL must have exactly its internal network and the matching instance label. Start the gateway with a maintenance Caddyfile generated by `runtime.route(config,null)` and the fixed gateway instance label. All templates use `restart:no`: provide reviewed systemd mount/service ordering; do not switch blindly to Docker autostart before the data volume is mounted.
7. Configure the exact approved recursive DNS addresses in `/etc/scop-staging/dns-resolvers`, confirm host name resolution uses them, then apply the dedicated-host firewall script only after confirming the staging marker, subnet non-overlap, IPv6 policy and provider firewall. Test from both authorized and unauthorized source addresses. Prove gateway direct outbound traffic is denied, app/DB cannot connect to any external target, agent reaches only the proxy, proxy refuses production Supabase/SAP/private addresses and unapproved websites, and database ports are not reachable externally. Record evidence and SHA-256 in `isolationApprovalSha256`. These external tests have not been performed here.
8. Configure operational monitoring: HTTPS/permission smoke from approved hospital/VPN locations, certificate expiry, state phase, failed GitHub deployment statuses, disk/backup age, memory, PostgreSQL health and canonical RFID/outbox failure queues. Docker logs are separate on this host; configure size/retention and a staging-only restricted collection destination. Do not ship patient data or secret environment dumps.
9. Review a separate activation PR changing the **staging-only** source flag and request job guard; production/publishing flags remain false. Build/pin its reviewed controller image. Set host `enabled=true`, `databasePrepared=true`, verified isolation digest and real hostname. Independently authorize creation of `ACTIVATION_APPROVED` and enable the mount-ordered controller service. The agent CMD uses `flock` to fence concurrent processes.
10. Run the first approved deployment request. Review GitHub **deployment status**, not merely request-workflow success: a successful package means queued request only. Exercise document 15's browser/UAT and real host rollback/reboot/crash tests before calling external staging accepted.

## Routine owner workflow after activation

Request enhancement → Codex draft PR → code CI/review/merge → isolated rehearsal → approve `scop-staging` request → agent verifies and deploys the exact capsule → view staging deployment status → hospital browser/UAT review. No routine owner Git, SSH, file-copy or standalone synchronization is required. For rollback/recovery, dispatch **Request persistent staging** on master with `rollback`/`recover` and the exact preserved previous SHA (or the recorded active SHA for reboot recovery); an independent environment approval is required. The agent never accepts a user-chosen arbitrary image or source branch.

Latest completed approved request is the desired operation; old requests are not replayed as a queue. Failed operations require a fresh request, while pending status acknowledgments retry independently. A missing/stale artifact, missing approval, incompatible DB or interrupted state blocks deployment.

## Activation blockers

No VPS, project/token, hostname, certificate, App, protected environment, persistent schema, runtime identity, attestation, isolation proof, backup/recovery drill, external browser/UAT or host monitoring has been provisioned/verified. Persistent DB bootstrap is intentionally a separate manual-governance blocker; this PR does not bypass frozen migration restrictions. App deployment metadata is not yet integrated into the existing production selector. None of these are implied by green code CI or the local synthetic rehearsal.

## Required local-integration gate

Require the **Persistent staging local integration / gateway** check on master in addition to Release quality and the Phase 3A rehearsal. The request packager verifies a successful same-commit master run, authenticated local-gateway receipt and matching source digest; missing or failed evidence blocks packaging. This CI workflow uses only disposable containers and generated local test certificates, not external staging. Browser client certificates are individually issued by approved hospital IT; keep the signing CA key offline, arrange short lifetimes/rotation and revoke app/VPN access on offboarding. No immediate TLS CRL/OCSP revocation support is claimed by this template.

## Required dedicated gateway-probe credentials

Before activation, install root-private `/etc/scop-staging/probe/server-ca.pem`, `client.crt`, and `client.key`. The CA file must validate the actual staging server certificate and hostname. Issue a dedicated short-lived probe client certificate trusted by the gateway's client CA, with client-auth usage; do not reuse a staff certificate, server key, production credential or application JWT. Arrange renewal/expiry alerts and individual revocation/rotation procedures before activation. Only the controller mounts this directory, read-only; no GitHub secret or frontend/backend mount is added.

For each post-switch check, the controller starts an ownership-labeled, network-isolated, short-lived probe using the exact frontend image ID. It receives the probe credentials through stdin (never command arguments or logs), joins only the internal ingress network, and has bounded runtime, response size, memory and process count. It validates HTTPS trust/SNI/mTLS, frontend HTML, `/health`, protected `/api/auth/me`, and commit/release response headers. Probe cleanup verifies full resource identity and image/purpose labels; it never removes a business worker, retained release, volume or shared network. Expired credentials or a broken proxy must block success and invoke recovery, rather than suppress TLS verification.

Before external acceptance, test GitHub outages during ACTIVE and interrupted states, loss of the handled cache, uncertain Docker effects, and real client/network failures with this corrected controller. The disposable integration now calls the same `agent.execute`, operation state machine and runtime adapter functions; private synthetic protocol fixtures are not authenticated deployment authority and are never exported as capsules. Local verification does not replace real host isolation, reboot, backup or hospital browser/UAT acceptance.
